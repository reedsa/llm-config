3. Use a todo list to plan and track your implementation steps before writing any code.

4. Implement the task. Follow all instructions in the repo's context file. Write focused,
   minimal changes — no refactors or cleanup beyond what the task requires.

5. Commit with a short imperative subject line referencing the issue (e.g. "Add foo bar (DRA-123)").

6. Do NOT open a pull request. The runner will invoke pre-pr-review.sh after this step,
   which runs multi-LLM review passes and opens the PR once any blockers are addressed.

7. When introducing shared state (e.g. `error`, `status`) that spans multiple steps or
   views in a multi-step UI flow, clear it on every step transition — not only before
   the next async call. Stale messages from one step will otherwise appear on unrelated screens.

8. When the task introduces a user-visible flow (navigation, form submission, data
   mutation), add the E2E test required by CLAUDE.md — do not rely on unit/component
   tests alone to satisfy that requirement.

9. When a runtime condition (e.g. missing auth context, null session value) would make
   a submit handler bail silently, include that condition in the form's canSubmit /
   disabled computation so the button is visually disabled rather than appearing pressable.

10. When rendering a group of accessibilityRole="radio" controls, wrap them in a View
    with accessibilityRole="radiogroup" and an accessibilityLabel describing the group.

11. When a label, placeholder, or descriptive text references a specific constraint
    (character length, format, allowed values), update it if the underlying constraint
    changes — stale copy misleads users about what input is valid.

12. When writing or editing a Cloud Build config (cloudbuild/*.yaml), use the
    built-in `$PROJECT_ID` substitution instead of hardcoding a literal GCP
    project ID — check whether the file already uses `$PROJECT_ID` elsewhere
    (e.g. image tags) and match it for consistency.

13. When a stateful connection handler (WebSocket, socket protocol, multi-message
    session) processes a message whose handling depends on state populated by an
    earlier message (e.g. a "setup"/handshake step), explicitly guard against
    that state being missing — close the connection with a clear reason rather
    than silently returning or letting a downstream call receive `undefined`.

14. When writing a Docker HEALTHCHECK (or any in-container loopback probe) that
    hits the app over HTTP, use `127.0.0.1` instead of `localhost` — Node 17+
    defaults `dns.lookup` to `verbatim=true`, resolving `localhost` to IPv6
    `::1` first, and a server bound only to `0.0.0.0` (IPv4) fails the check
    with `ECONNREFUSED`.

15. When configuring a Cloud Run `--startup-probe`, budget at least 30-45
    seconds of total allowance (`periodSeconds` × `failureThreshold`) for
    Node.js/Next.js cold starts — a tight threshold (e.g. 3s × 3 = 9s) can
    trigger a crash-restart loop before the app finishes booting. Liveness
    probes don't need the same headroom since they gate ongoing health, not
    initial startup.

16. When adding a new internal module to a package whose index.ts re-exports
    everything (`packages/*/src/index.ts`), import shared internals (env
    checks, config helpers) from a dedicated leaf module - never import
    back from index.ts itself. That creates a circular dependency between
    index.ts and the new module, which can resolve to `undefined` at
    runtime depending on import order.

17. When a file gains a new real (non-type-only) import from a workspace
    package (`@rivermount/shared`, etc.), check whether the consuming
    app's `vitest.config.ts` has a `resolve.alias` pointing that package
    at its source (`src/index.ts`) rather than relying on its built
    `dist/` output. CI's Test job runs before any build step, so a
    package resolved via `dist/index.js` fails to resolve in a fresh
    checkout even though it works locally once you've built it once.

18. When writing a script that performs destructive/mutating operations
    against a shared environment (a migration, backfill, or bulk-write
    script), require the target project/database to be set explicitly
    and exit with an error if it's missing - never fall back to a
    hardcoded production project ID as a default. An operator running it
    locally without the right env vars set would otherwise silently
    write to production.

19. When writing to a Firestore field that holds a nested object (e.g.
    `metadata`) via `.update()` or another partial-write call, merge with
    the field's existing parsed value first if you only mean to change
    one key. `.update()` replaces the whole field value - it does not
    deep-merge nested objects the way it merges separate top-level field
    paths.
