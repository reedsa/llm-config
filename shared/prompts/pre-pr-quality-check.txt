Review the following changeset for code quality issues before a PR is opened.

You will be shown the diff plus the full current text of each modified
file (under `## File: <path>`). Use the file context to evaluate siblings
of changed code, not just the diff itself.

Focus on:
- Correctness: logic errors, missing edge cases, off-by-ones
- Clarity: confusing names, unclear intent, missing context
- Maintainability: duplication, brittle patterns, missing tests for new behaviour
- API contracts: broken interfaces, incorrect error handling
- Test value space: tests should cover realistic inputs (decimals,
  negatives, empty/large values, boundary conditions), not only round
  integers or happy-path placeholders. Flag suites that exercise only
  trivial values when the production code handles a wider range.
- Guard-clause tests: every new validation guard or thrown error (`if (!valid) throw`,
  early-return checks, etc.) must have at least one test that exercises the error path.
  Flag guards that are added in production code but have no corresponding test.
- Test sequencing: expected values used in assertions must be captured *before* the
  code under test runs. Capturing a `new Date()` or similar after the call creates a
  timing race. Flag any test where a computed expected value is derived after the
  subject call.
- Mock-layer consistency: a test must mock the same module the subject imports from.
  If the component imports `foo` from `../../lib/auth`, the test must mock `../../lib/auth`,
  not a transitive dependency like `firebase/auth`. Flag mismatches.
- Form-control disabled state: when a test asserts that a guard prevents form submission,
  also verify the control's disabled state (e.g. `accessibilityState?.disabled === true`),
  not only the absence of side-effects like a mock not being called.
- Firestore rules / client consistency: when a PR tightens a security rule's field
  constraint (type, format, range), check whether `lib/` client code still produces
  values that satisfy the new constraint — empty-string sentinels, default values written
  on creation, and intermediate states (e.g. `accentColor: ''`) are common failure modes.
- Firestore `existsAfter` test pairing: when a rule is changed from `exists()` to
  `existsAfter()` to permit atomic batch writes, the rules test suite must include both
  a positive case (valid batch succeeds) and a negative counterpart (same batch structure
  with invalid/missing prerequisites fails), confirming the guards behind `existsAfter`
  are still load-bearing.
